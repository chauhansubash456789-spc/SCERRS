CHAPTER 1: INTRODUCTION

1.1 Background of the Project

Emergency response is a time-critical activity in which every second counts. In Nepal, natural disasters such as earthquakes, floods, and landslides, together with daily road accidents, fires, and medical emergencies, place persistent pressure on limited response resources. Traditional methods of reporting emergencies — phone calls to separate control rooms, manual note-taking, and paper-based records — are slow, error-prone, and fragmented across multiple agencies. There is often no single channel through which a citizen can report a situation and track its resolution, and no shared view for the agencies that must coordinate.

SCERRS (Smart Citizen Emergency Reporting & Response System) addresses this gap by providing a unified, web-based platform. Citizens can report an emergency in seconds with automatic GPS location capture and photo evidence. The report is automatically routed to the correct responding agency based on the incident category, and the status is tracked in real time through a transparent workflow. This reduces response time, improves coordination between agencies, and increases transparency for the citizen.

1.2 Problem Statement

In the current emergency reporting landscape of Nepal there is a lack of an integrated, digital reporting system. The identified problems are:

  • No single channel for citizens to report an emergency and provide precise location and photo evidence.
  • Manual routing of reports to the correct agency causes delays and misdirection.
  • No real-time status tracking for citizens once a report is submitted.
  • Limited coordination and shared situational awareness between responding agencies.
  • No centralized analytics to guide resource planning and preparedness.

1.3 Objectives

The main objectives of the project are:

  1. To design and develop a web-based emergency reporting system for citizens.
  2. To enable automatic routing of reports to the correct responding agency.
  3. To provide role-based dashboards for citizens, authorities, and administrators.
  4. To offer real-time status tracking and notifications.
  5. To present an interactive live map and analytics dashboard for situational awareness.
  6. To build a secure system using modern authentication and data-protection practices.

1.4 Scope of the Project

The system covers the full lifecycle of an emergency report: citizen registration and login; incident reporting with category, severity, GPS, address, and photo evidence; automatic routing to a department; authority acknowledgment, dispatch, and resolution; team assignment; status history auditing; in-app notifications; citizen feedback; and an analytics dashboard. The scope is limited to a web application (not a native mobile app), spans five departments (Police, Fire Brigade, Ambulance, Municipality, and Disaster Management), and supports three user roles (citizen, authority, admin).

1.5 Feasibility Study

Technical Feasibility

The system uses mature, freely available technologies — PHP, MySQL, Bootstrap, Chart.js, and Leaflet/OpenStreetMap — all well documented and suited to the developers' BCA-level skills. No specialized hardware is required beyond a standard web server and internet-enabled client devices with GPS. Hence it is technically feasible.

Operational Feasibility

Role-based interfaces map directly to each user group's workflow, and the web interface requires no client installation. Thus it is operationally feasible.

Economic Feasibility

All components are open source; development runs on a free Laragon stack. No licensing or proprietary hardware costs are involved, making the project economically feasible.

3.4 Database Schema Design

The database, named scerrs, uses InnoDB engine with utf8mb4 charset. The principal tables are described below.

Table: users

Field Type Constraints
id INT UNSIGNED PK, AUTO_INCREMENT
name VARCHAR(120) NOT NULL
email VARCHAR(150) UNIQUE, NOT NULL
password VARCHAR(255) NOT NULL
role ENUM(citizen,authority,admin) DEFAULT 'citizen'
department_id INT UNSIGNED FK → departments(id) ON DELETE SET NULL
active TINYINT(1) DEFAULT 1

Table: incidents

Field Type Constraints
id INT UNSIGNED PK, AUTO_INCREMENT
ref_no VARCHAR(20) UNIQUE, NOT NULL
user_id INT UNSIGNED FK → users(id) ON DELETE CASCADE
category_id INT UNSIGNED FK → categories(id)
title VARCHAR(150) NOT NULL
description TEXT NOT NULL
latitude / longitude DECIMAL(10,7) NOT NULL
address VARCHAR(255) NULL
severity ENUM(low,medium,high,critical) DEFAULT 'medium'
status ENUM(pending,acknowledged,in_progress,resolved,rejected) DEFAULT 'pending'

The same discipline is applied to the remaining tables — categories, incident_media, response_teams, assignments, status_histories, notifications, and feedback — each with appropriate foreign keys and indexes to preserve referential integrity and query performance.

3.5 Request-Routing / Department Mapping

A central design decision is that each incident is automatically routed to one department determined by its category. The category-to-department mapping (from seed data) is:

Department Categories
Nepal Police Road Accident, Crime / Violence
Fire Brigade Fire Outbreak
Ambulance Services Medical Emergency
Municipality Fallen Tree / Debris, Road Hazard, Electricity Hazard
Disaster Management Agency Flood, Landslide, Earthquake Damage

Consequently, an authority dashboard only shows incidents whose category.department_id equals the authority's own users.department_id. This by-design isolation is a key behavior verified during testing.

CHAPTER 4: IMPLEMENTATION AND TESTING

4.1 Implementation Approach

The system was built with a modular, procedural PHP structure keeping concerns separated for maintainability. The includes/ folder holds shared header, footer, and security/helper functions; each role uses its own directory (citizen/, authority/, admin/); reusable JSON endpoints live in api/.

4.2 Module Implementation Details

Module A — Authentication & Session Management

Implemented in auth/login.php, auth/register.php, and auth/logout.php. Registration distinguishes citizen and authority/ admin fields. Passwords are hashed with password_hash() (bcrypt) and verified with password_verify(). On login, session_regenerate_id(true) prevents session fixation. Helper functions current_user() and require_role() gate access by role.

// login.php (simplified)
if (password_verify($password, $user['password'])) {
    session_regenerate_id(true);
    $_SESSION['user_id'] = (int)$user['id'];
    redirect($allow['role_home'][$user['role']]);
}

Module B — Incident Reporting

Implemented in citizen/report_new.php. Captures category, title, description, severity, GPS, and up to five photos. A unique reference number is generated as INC-YYYY-XXXX. Inputs are validated, photo MIME types and sizes are checked (image, ≤ 5 MB), and a database transaction inserts the incident and each media row atomically.

$pdo->beginTransaction();
insert('incidents', $incident);
$incidentId = $pdo->lastInsertId();
foreach ($files as $f) insert('incident_media', ['incident_id'=>$incidentId, 'file_path'=>$f]);
$pdo->commit();

Module C — Routing & Response Workflow

Implemented in authority/incident_view.php. The authority can update the status (acknowledge, in_progress, resolved, rejected) with an optional note, and assign response teams from their department. Each change is inserted into status_histories for the audit trail, and a notification is created for the reporting citizen.

Module D — Live Map

Implemented in authority/dashboard.php with api/map_data.php. On load, loadMarkers() fetches routed incidents via AJAX and renders Leaflet circle markers whose color and radius encode severity (low→green, medium→yellow, high→orange, critical→red).

Module E — Analytics Dashboard

Implemented in authority/analytics.php with api/analytics_data.php. Aggregated queries feed four Chart.js charts: incidents by category (bar), severity distribution (doughnut), status pipeline (pie), and a 14-day trend (line). Loading spinners, empty states, and error handling are included.

Module F — Notifications & Feedback

The navbar shows an unread-notification badge; citizens can mark notifications read and can submit a star rating plus optional comment on resolved incidents, stored in feedback with a uniqueness constraint per incident–user pair.

CHAPTER 5: CONCLUSION AND FUTURE RECOMMENDATIONS

5.1 Lessons Learnt

  • Careful relational design with foreign keys is essential to avoid data-integrity and routing errors.
  • Security basics — prepared statements, bcrypt hashing, CSRF tokens, and RBAC — are mandatory for a multi-user web system.
  • Agile, incremental development (auth → reporting → routing → response → analytics) enabled systematic testing and refinement.
  • The correctness of agency routing depends entirely on the category–department mapping, which governs which authority sees an incident.
  • Clear, emergency-appropriate UI with role-specific dashboards materially improves usability.

5.2 Conclusion

The SCERRS system has been successfully designed, implemented, and tested. It fulfils the project objectives: one-tap emergency reporting with auto GPS and photo evidence, automatic agency routing by category, severity classification, role-based dashboards, live status tracking, an interactive map, analytics, notifications, and feedback. The system gives citizens a fast, transparent way to report emergencies and gives agencies the tools to prioritize, dispatch, and manage responses efficiently — addressing the real challenge of slow, fragmented emergency reporting in Nepal.

5.3 Future Recommendations

  1. Develop native Android/iOS apps for offline capability and push notifications.
  2. Add Nepali (and other regional) language support.
  3. Use WebSockets/SSE for real-time push updates instead of polling.
  4. Apply machine learning to auto-classify severity from uploaded photos.
  5. Integrate SMS/email gateways and agency dispatch systems.
  6. Add predictive analytics for incident hotspots and resource demand.
  7. Provide an AI chatbot to help citizens describe incidents conversationally.
  8. Strengthen security with audit logs, encryption at rest, and WCAG accessibility.
